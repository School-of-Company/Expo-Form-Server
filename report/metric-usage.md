# 성능 지표 측정 사용법

이 문서는 성능 지표 측정 명령의 사용법과 출력 읽는 법을 설명합니다. 1장은 프로젝트와 무관하므로 다른 프로젝트나 에이전트 지침에 그대로 복사할 수 있습니다. 2장과 3장은 이 프로젝트(Expo-Form-Server)에만 해당합니다.

- 결과 형식: `report/metric-schema.md`
- 계획: `report/metric-plan.md`

## 1. 공통 (프로젝트 무관)

### 1.1 명령

```bash
pnpm perf:measure
```

- 이 명령은 측정을 실행하고, 결과를 표로 터미널에 출력합니다.
- 측정이 실패하면 0이 아닌 종료 코드로 끝납니다. 측정은 다음 두 경우에 실패합니다.
  - `invariant` 지표의 표본 값이 서로 다를 때
  - `stable`이 아닐 때(같은 실행에서 두 번 잰 값이 다를 때)
- 측정이 실패해도 결과 파일이 있으면 표를 출력합니다.
- 상한 초과는 이 명령이 판정하지 않습니다. 상한은 리뷰를 거친 상한 파일로 CI가 판정합니다.

구성 파일:

| 파일                    | 역할                                                            | 다른 프로젝트로 옮길 때            |
| ----------------------- | --------------------------------------------------------------- | ---------------------------------- |
| `perf/metric-report.ts` | 결과 JSON을 씀                                                  | 그대로 복사                        |
| `perf/print-report.mjs` | 결과 JSON을 표로 출력(`node perf/print-report.mjs <결과 폴더>`) | 그대로 복사                        |
| `perf/measure.sh`       | 측정을 실행하고 표를 출력                                       | 맨 위 "프로젝트 설정" 두 줄만 바꿈 |
| 측정 spec               | 프로젝트 고유 측정                                              | 새로 씀                            |

### 1.2 출력 읽는 법

```
## <metricSet>: <title>
| 지표 | id | kind | 값 | 단위 | 표본 | 표본 일치 |
...
stable: 예
params: ...
env: ...
결과 파일: <경로>
<details 키> (<개수>)
  <항목>
```

| 칸               | 뜻                                                 | 확인할 것                                                                                       |
| ---------------- | -------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| kind `invariant` | 조건(예: 데이터 양)을 바꿔도 값이 같아야 하는 지표 | "표본 일치"가 `아니오`면 데이터 양에 따라 비용이 늘어납니다(예: N+1 쿼리). 바로 고칩니다        |
| kind `max`       | 고정 조건에서 잰 크기. 작을수록 좋음               | 바꾸기 전 값과 비교합니다. 늘었으면 이유를 설명할 수 있어야 합니다                              |
| 값               | 결과 JSON의 `value`와 같은 값                      | 단위를 함께 읽습니다(`count`, `bytes` 등)                                                       |
| stable           | 같은 실행 안에서 두 번 잰 값이 같았는지            | `아니오`면 측정이 흔들리는 것입니다. 숫자를 믿지 말고 원인(시각, 랜덤 값, 정렬)을 먼저 찾습니다 |
| details          | 실행된 쿼리 등 원본 목록                           | 값이 바뀌었으면 여기서 무엇이 추가되거나 빠졌는지 봅니다                                        |

### 1.3 에이전트 지침 (복사해서 씀)

- 측정 대상 코드를 바꾸면, 바꾸기 전과 뒤에 `pnpm perf:measure`를 각각 실행합니다.
- 두 표를 비교해 PR 설명에 바뀐 지표만 적습니다. 지표, 전, 후, 이유를 적습니다.
- "표본 일치"가 `아니오`이거나 `stable`이 `아니오`이면 작업을 끝내지 않습니다. 원인을 고치거나 보고합니다.
- 값이 늘었는데 이유를 설명할 수 없으면, 늘어난 이유를 details에서 찾습니다.
- 상한 파일은 지시 없이 바꾸지 않습니다.
- 측정 spec의 시드나 조건을 바꾸면 값의 뜻이 바뀝니다. 바꿨다면 반드시 PR 설명에 적습니다.

## 2. 이 프로젝트 고유

### 2.1 실행 조건

- `DATABASE_URL`이 없으면 Docker로 임시 Postgres(다이제스트 고정 `postgres:17-alpine`)를 띄우고, 끝나면 지웁니다. 그래서 Docker가 실행 중이어야 합니다.
- 결과 파일은 `$RUNNER_TEMP/perf-metrics/public-answers.json`에 씁니다. `RUNNER_TEMP`가 없으면 OS 임시 폴더를 만들어 쓰고, 다시 볼 수 있게 남깁니다.
- CI(`.github/workflows/perf-metrics.yml`)도 같은 명령을 실행합니다.

### 2.2 측정 대상과 조건

- 대상: `GET /internal/surveys/:expoId/public-answers`. 측정 spec은 `test/metrics/public-answers.metrics-spec.ts`입니다.
- 조건: 응답 N=250(바이트 지표 기준), 2N=500, 문항 3개와 30개, limit=100, 다른 설문 응답 1,000행.

| id                                  | kind      | 뜻                                                            |
| ----------------------------------- | --------- | ------------------------------------------------------------- |
| `queries.firstPage`                 | invariant | 첫 페이지 요청 한 번의 SQL 수. N, 2N, 문항 30개에서 같아야 함 |
| `queries.nextPage`                  | invariant | 두 번째 페이지 요청 한 번의 SQL 수                            |
| `bytes.firstPage`, `bytes.nextPage` | max       | N=250에서 페이지 응답 본문 바이트                             |
| `bytes.total`                       | max       | N=250을 끝까지 받은 바이트 합                                 |
| `bytes.perRow`                      | max       | `answers` 배열만의 바이트 합 ÷ N                              |

1단계(PR #323)에서 Actions로 잰 값은 쿼리 수 첫 페이지 7, 다음 페이지 2이고, 바이트는 16,746 / 16,746 / 42,052 / 159입니다. 이 값은 아직 상한이 아닙니다. 상한은 2단계에서 사람이 정합니다.

## 3. 성능 위험 유형

이 프로젝트를 조사하면서 코드로 확인한 유형만 적습니다. 아래 위치는 실제로 느리다고 측정된 곳이 아니라, 데이터가 늘면 비용이 함께 늘어나는 구조가 확인된 곳입니다. 측정 지표가 있는 곳은 따로 표시합니다.

### 3.1 페이징 없는 목록

한 번의 요청이 조건에 맞는 행을 모두 돌려줍니다. 행 수가 늘면 응답 크기와 조회 시간이 함께 늘고, 호출자가 크기를 제한할 방법이 없습니다.

| 위치                                     | 근거                                                                                                                                                                                           |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /forms/expos/:expoId/program-forms` | `src/form/program-form.controller.ts:88-93`가 `findProgramsByExpo`를 부르고, `src/form/form.store.ts:189-195`의 `find`에 `take`/`limit`가 없습니다. 열은 `HEADER_COLUMNS`로 줄였습니다(`:191`) |

- 측정 지표: 없음. 계획 단계에서 이번 대상에서 뺐습니다.
- 박람회 하나에 프로그램 폼이 몇 개까지 생기는지는 확인하지 못했습니다.

### 3.2 필요 없는 필드까지 전체를 읽음

호출한 쪽이 일부 값만 쓰는데, 저장소가 행 전체(큰 jsonb 열 포함)를 읽어 옵니다.

| 위치                         | 쓰는 값          | 읽는 값                       | 근거                                                                                                                                                                                                               |
| ---------------------------- | ---------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 프로그램 폼 관리자 권한 가드 | `expoId` 하나    | 폼 전체(입력 필드 jsonb 포함) | `src/form/program-admin-access.guard.ts:37-42`, `src/form/form.store.ts:182-186`(`select` 없음)                                                                                                                    |
| 내 설문 응답 상태 조회       | `survey.id` 하나 | 설문 전체(문항 jsonb 포함)    | `src/survey/survey-answer.service.ts:67-76`이 `resolveRespondent`를 부르고, `:204`가 `findByExpoAndType`을 씁니다. 문항을 빼고 읽는 `findHeaderByExpoAndType`이 이미 있습니다(`src/survey/survey.store.ts:96-108`) |

- 측정 지표: 없음.

### 3.3 페이지마다 같은 데이터를 반복함

페이지로 나눈 응답이 페이지마다 바뀌지 않는 데이터를 다시 싣거나 다시 조회합니다. 전체를 받는 비용이 "페이지 수 × 반복분"만큼 늘어납니다.

| 위치                                                              | 근거                                                                                                                   |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `GET /internal/surveys/:expoId/public-answers` 응답의 `questions` | `src/survey/survey-public.service.ts:112-120`이 페이지마다 문항 정의 전체를 응답에 싣습니다                            |
| 같은 엔드포인트의 설문 조회                                       | 페이지마다 `findPublicSurvey`가 설문 행을 문항까지 다시 읽습니다(`src/survey/survey-public.service.ts:94`, `:167-177`) |

- 측정 지표: 있음. 1단계 측정에서 다음 페이지의 SQL 2개 중 하나가 설문 조회였습니다(`sql.nextPage`). 첫 페이지와 다음 페이지의 바이트가 16,746으로 같았습니다. 다음 페이지에도 `questions`가 그대로 실린다는 뜻입니다.
- 문항 수를 30개로 늘려도 쿼리 수는 같았습니다. 반복되는 것은 쿼리 수가 아니라 바이트입니다.

## 4. 확인하지 못한 것

- 이 사용법과 결과 형식이 다른 프로젝트(NestJS가 아닌 스택 포함)에 충분한지는 확인하지 못했습니다.
- `perf/measure.sh`는 Bash와 Docker가 있다고 가정합니다. Windows에서는 시험하지 않았습니다.
- 3장의 위치가 운영에서 실제로 느린지는 측정하지 않았습니다.
